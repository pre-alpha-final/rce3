RemoteControlledElectronics Next Version Project Plan

Build a smaller, easier-to-use successor to the existing RCE project: a minimal ephemeral feed service where clients can post raw request bodies to a feed and readers can long-poll that feed without schemas, message types, or required client libraries.

Reference: rce2 concept only Primary goal: pick up and use Core pattern: POST plus long polling Retention: inactive feeds expire after 24h

Product Direction

North Star Make remote electronics control feel like writing to and reading from a temporary shared pipe over HTTP.
Design Rule Do not add formats, types, sessions, sender identities, or receiver identities unless they are required for correctness.
User Promise A user can create a feed implicitly, post arbitrary data, and connect multiple independent readers with almost no setup.
Operational Promise Feeds are temporary, simple to reason about, and automatically cleaned up after inactivity.

Scope

In Scope

  • HTTP endpoints for feed help, posting messages, long-polling reader queues, and resetting reader queues.
  • Implicit feed creation on first valid request.
  • Feed mode selection at creation: open or Authorization-key protected.
  • Pass-through message bodies with minimal server interpretation.
  • Multiple readers per feed, each with its own queue.
  • Feed expiration after 24 hours without GET or POST activity.
  • Reader cleanup when the parent feed expires.
  • Bare-bones browser-readable help at GET /feed-guid.

Design Boundaries

  • User accounts, sender identity, receiver identity, and delivery acknowledgements.
  • Message schemas, type negotiation, format validation, or special device protocols.
  • Persistent history after feed deletion.
  • Per-reader authentication beyond the feed-level mode.
  • Administrative dashboards in the product surface.

API Contract

Endpoint Purpose Request Response
GET /{feedGuid} Create or touch a feed, then show minimal integration help. Optional Authorization key only if creating or accessing a protected feed. Plain text or simple HTML help with the three endpoint patterns and auth rule.
POST /{feedGuid} Publish the request body to every active reader queue on the feed. Raw body. No required content type. Auth must match the feed mode exactly. Small success response after the message is accepted for distribution.
GET /{feedGuid}/{readerGuid} Create or touch a reader queue and long-poll for the next message. Auth must match the feed mode exactly. Return one queued message at a time using the original message Content-Type, or return an empty timeout response after 30 seconds.
GET /{feedGuid}/{readerGuid}/reset Clear a reader queue, make it usable again after overflow, and redirect to it. Auth must match the feed mode exactly. Redirect to GET /{feedGuid}/{readerGuid}.

Recommended Status Codes

  • 200 OK for help, successful post acceptance, and successful long-poll message delivery.
  • 204 No Content when a long-poll request times out after 30 seconds with no messages.
  • 400 Bad Request for malformed feed GUIDs, malformed reader GUIDs, or unusable request paths.
  • 401 Unauthorized when a protected feed is accessed without the correct Authorization key.
  • 403 Forbidden when an open feed is accessed with an Authorization key, because protected access to an open feed is explicitly invalid.
  • 413 Payload Too Large when a message exceeds the configured maximum body size.
  • 500 Internal Server Error when a reader queue has exceeded its configured size limit and has become unusable until reset.

Lifecycle Rules

Feed Lifecycle

  1. Any valid request for a missing feed creates that feed.
  2. If the creation request includes an Authorization key, the feed becomes protected and that supplied key becomes the feed key.
  3. If the creation request has no Authorization header, the feed becomes open.
  4. The selected mode is permanent for the life of the feed.
  5. Protected feeds require a matching Authorization key on every request.
  6. Open feeds require no Authorization key; requests that include one are rejected.
  7. Each valid GET or POST updates the feed activity timestamp.
  8. A feed is deleted after 24 hours without any valid GET or POST activity.

Reader Lifecycle

  1. GET /{feedGuid}/{readerGuid} creates a reader queue.
  2. Each message posted to a feed is appended to every active reader queue for that feed.
  3. Readers receive their own posted messages because the system has no sender identity.
  4. GET /{feedGuid}/{readerGuid}/reset clears a reader queue, fixes it if it was marked unusable, and redirects to it.
  5. Readers are deleted when their parent feed is deleted.

Implementation Plan

Phase 1: Foundation
  • Select the runtime and HTTP framework for the new service.
  • Create route parsing for /{feedGuid} and /{feedGuid}/{readerGuid}.
  • Require feed and reader IDs to parse cleanly as C# Guid values and add clear bad-path handling.
  • Add configuration for port, poll timeout, feed TTL, and max message size.
Phase 2: Feed Handling
  • Implement feed creation on first valid request.
  • Store feed mode, hashed protected key, reader list, and last activity timestamp.
  • Enforce exact auth-mode matching for open and protected feeds.
  • Return bare-bones help for GET /{feedGuid}.
Phase 3: Reader Queues
  • Create reader queues on first reader request.
  • Queue messages independently for each reader.
  • Define queue backpressure limits so inactive readers cannot exhaust memory.
  • Mark a reader unusable when its queue exceeds the configured limit; future reads return 500 with an appropriate description until the reader queue is reset.
Phase 4: Long Polling
  • Return immediately when a reader already has queued messages.
  • Return exactly one queued message per long-poll response for maximum transparency.
  • Hold pending reader requests for up to 30 seconds.
  • Wake pending readers as soon as a new message arrives.
  • Handle disconnects, cancellations, and server shutdown cleanly.
Phase 5: Expiration
  • Run a periodic cleanup job for feeds inactive for 24 hours.
  • Delete all reader queues owned by an expired feed.
  • Complete pending reader polls before or during deletion with a clear empty response.
  • Add metrics or logs for creation, post, timeout, rejection, and expiration events.
Phase 6: Hardening
  • Add request size limits, slow-client protection, and concurrency tests.
  • Document operational limits and deployment settings.
  • Create example curl commands for open and protected feeds.
  • Prepare a minimal release package and smoke-test script.

Runtime Notes

  • There is no public data model, message model, envelope, type registry, or required format.
  • The service keeps only the private in-memory state needed to route messages, enforce feed mode, hold reader queues, and expire inactive feeds.
  • Feed mode is either open or protected and cannot change after creation.
  • Feed and reader GUIDs must be valid C# Guid values.
  • The server preserves the posted body and returns the original Content-Type when the message is read.

Testing Plan

  • Contract tests: verify all three endpoint shapes, expected status codes, body pass-through, and timeout behavior.
  • Auth tests: cover open feed creation, protected feed creation, wrong key, missing key, and protected request sent to an open feed.
  • Queue tests: prove that each reader receives every feed message independently, including messages posted by the same client, one message per read response.
  • Content tests: verify that the original Content-Type is preserved when a message is returned to a reader.
  • Expiration tests: delete feeds after 24 hours of inactivity and remove their readers.
  • Overflow tests: verify that a reader whose queue exceeds the configured size limit becomes unusable and returns 500 with a useful description.
  • Load tests: simulate many long-poll readers and bursty posts to validate memory and concurrency limits.
  • Network tests: verify cancellation behavior when clients disconnect before a long-poll response.

Operational Decisions

  • Set a maximum message body size before launch. The project can stay format-free while still protecting the service from unbounded memory use.
  • Set a maximum queued messages or queued bytes per reader. When the limit is exceeded, mark that reader unusable and return 500 with an appropriate description for future reads.
  • Hash stored Authorization keys instead of keeping feed keys in plain text.
  • Use monotonic or injected clocks in tests so 24-hour expiration is reliable and fast to verify.
  • Prefer simple structured logs even if the public API remains unstructured.
  • Use memory-only storage for this version. Feeds and readers disappear on process restart.

Risks and Mitigations

Unbounded Queues Inactive readers can accumulate messages forever during a feed lifetime. Add queue limits and a documented overflow policy.
Long-Poll Resource Use Many connected readers can consume file descriptors and memory. Use efficient async handling and test with realistic concurrency.
Auth Ambiguity Open feeds reject Authorization keys and protected feeds require them. Keep this strict rule visible in help text and tests.
Restart Semantics Feeds disappear on restart because this version is memory-only. Document this clearly in the help text and README.
GUID Guessing Feed and reader GUIDs act as capability URLs. Require values that map into C# Guid and recommend random values in docs.
Message Interpretation Adding conveniences can slowly create formats. Keep the server pass-through and move device-specific behavior to clients.

Milestones

  1. Prototype: in-memory feeds, POST fanout, and reader long polling working locally.
  2. Contract Complete: strict auth mode behavior, reader uniqueness, help page, and status codes covered by tests.
  3. Lifecycle Complete: feed inactivity expiration and reader cleanup implemented and tested.
  4. Hardening Complete: request limits, queue limits, cancellation handling, logs, and load smoke tests in place.
  5. Release Candidate: README examples, deployment notes, and a clean end-to-end smoke test for open and protected feeds.
